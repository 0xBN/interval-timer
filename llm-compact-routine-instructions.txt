COMPACT TIMER URL FORMAT: SOURCE OF TRUTH

Use this spec as the exact format definition for generating or consuming timer routines.

If you are updating another repo:
- implement this format exactly
- do not invent alternate syntax
- do not assume deprecated params like `cd`

Core design goal:
- this format is audio-first
- a user should be able to follow the routine without looking at the screen
- preserve spoken setup cues and spoken transition cues, not just timings


1. URL SHAPE

Active format:

`?x=<compact-routine>`

Deprecated compatibility format:

`?r=<url-encoded-json>`

If building new functionality, only use `?x=...`.


2. TOP-LEVEL STRUCTURE

The `x` param value is a compact routine string:

`Routine Name~Label Section 1~Pattern 1~Label Section 2~Pattern 2~...`

Rules:
- first segment is always the routine name
- after that, segments come in pairs
- each pair is:
  - label section
  - pattern section
- therefore, total segment count must be odd

Example:

`Abrahangs~4-finger half crimp~p5@3,w10@3,r20,w10@3`


3. LABEL SECTIONS

There are two valid label section forms:

1. `Work Label`
2. `Work Label^Prepare Label`

Meaning:
- `Work Label`
  - work blocks use this label
  - prepare blocks also use this label
- `Work Label^Prepare Label`
  - work blocks use `Work Label`
  - prepare blocks use `Prepare Label`

Examples:

- `4-finger half crimp`
- `Front-2 open^Front-2 open, index and middle`

Guidance:
- use `Prepare Label` when the spoken setup cue should be more explicit than the work label
- prefer full spoken phrases over short visual labels when the routine is intended for hands-free use


4. PATTERN SECTIONS

Pattern sections are comma-separated token lists:

`token,token,token,...`

Examples:

- `p5@3,w10@3,r20,w10@3`
- `p5@3,w10@3,r6^Switch to left side,w10@3,r8^Rest`


5. TOKEN GRAMMAR

There are two token forms:

Prepare/work token:

`<type><duration>[ @<countdown> ][ ! ]`

Rest token:

`r<duration>[ @<countdown> ][ ^<rest_label> ][ ! ]`

Practical forms:
- `p5`
- `p5@3`
- `w30@10`
- `r20`
- `r6^Switch to left side`
- `r10!`
- `r10^Rest!`

Definitions:
- `type`
  - `p` = prepare
  - `w` = work
  - `r` = rest
- `duration`
  - integer number of seconds
- `@<countdown>`
  - optional
  - sets `countdown_last`
- `^<rest_label>`
  - optional
  - valid for rest tokens
  - gives the rest block spoken text
  - use this for transitions like `Switch sides`, `Shake it out`, or `Move to the floor`
- `!`
  - optional
  - sets `skip_on_last: true`
  - currently intended for final rest-style blocks
  - if present, it must appear only as the final character of the token

Parsing note:
- `^` has different meanings in different contexts
- in label sections, `Work Label^Prepare Label` splits work vs prepare labels
- in pattern sections, only rest tokens may use `^<rest_label>`
- for rest tokens, if `^` is present, the rest label is all text after `^` up to an optional trailing `!`
- example: `r10^Rest!` parses as:
  - duration `10`
  - label `Rest`
  - `skip_on_last: true`


6. TOKEN SEMANTICS

Examples:

- `p5`
  - prepare, duration 5
- `p5@3`
  - prepare, duration 5, countdown_last 3
- `w30@10`
  - work, duration 30, countdown_last 10
- `r20`
  - rest, duration 20
- `r6^Switch to left side`
  - rest, duration 6, spoken label `Switch to left side`
- `r10!`
  - rest, duration 10, skip_on_last true
- `r10^Rest!`
  - rest, duration 10, spoken label `Rest`, skip_on_last true


7. BLOCK EXPANSION MODEL

Consumers should expand the compact format into the equivalent internal block array.

Expansion rules:
- `p...` creates a block:
  - `type: "prepare"`
  - `label: prepare label`
- `w...` creates a block:
  - `type: "work"`
  - `label: work label`
- `r...` creates a block:
  - `type: "rest"`
  - no label by default unless the token provides `^<rest_label>`
- `@N` becomes:
  - `countdown_last: N`
- `^<rest_label>` becomes:
  - `label: <rest_label>`
- `!` becomes:
  - `skip_on_last: true`

Audio-first interpretation:
- use unlabeled `r...` only for true generic recovery periods
- if the user needs spoken guidance during a rest, the rest token should carry `^<rest_label>`
- do not silently drop meaningful rest speech during conversion


8. EXAMPLE EXPANSION

Compact input:

`Grip A^Grip A, get set~p5@3,w10@3,r20^Shake it out,w10@3,r10^Rest!`

Expanded blocks:

```json
[
  { "type": "prepare", "label": "Grip A, get set", "duration": 5, "countdown_last": 3 },
  { "type": "work", "label": "Grip A", "duration": 10, "countdown_last": 3 },
  { "type": "rest", "label": "Shake it out", "duration": 20 },
  { "type": "work", "label": "Grip A", "duration": 10, "countdown_last": 3 },
  { "type": "rest", "label": "Rest", "duration": 10, "skip_on_last": true }
]
```

10. AUDIO-FIRST EXAMPLE

Compact string:

`Single leg bridge^Right side ready~p5@3,w30@10,r6^Switch to left side,w30@10,r10^Rest!`

Meaning:
- prepare speaks `Right side ready`
- first work block uses `Single leg bridge`
- rest speaks `Switch to left side`
- second work block uses `Single leg bridge`
- final rest speaks `Rest`

11. RESERVED CHARACTERS

These characters have syntax meaning and should not appear raw in labels unless your producer and consumer both agree on an escaping scheme:

- `~`
- `^`
- `,`
- `@`
- `!`

If generating labels for this format, avoid those characters in labels.

The letter `x` is not reserved in labels.


12. GENERATION RULES FOR LLMS

If generating a compact routine string:
- output only the compact routine string unless asked otherwise
- keep all spoken labels fully explicit
- use `@N` on any token that needs a countdown
- write repeated blocks explicitly
- use `r<duration>^<spoken text>` when a rest block needs spoken transition guidance
- do not collapse spoken transition rests into silent `r...` blocks
- use `!` only when the block should become `skip_on_last: true`
- do not output JSON unless explicitly requested


13. CONSUMER RULES FOR IMPLEMENTATIONS

If implementing a parser in another repo:
- split on `~`
- validate odd segment count and label/pattern pairing
- split label section on the first `^`
- split pattern section on `,`
- parse prepare/work tokens separately from rest tokens
- treat `!` only as a terminal suffix
- for rest tokens, if `^` exists, treat everything after `^` as the spoken rest label except a trailing `!`
- map `@N` to `countdown_last`
- map rest-token `^label` to `label`
- map `!` to `skip_on_last`
- build the equivalent internal routine object
- preserve spoken rest cues so the routine remains hands-free friendly

Recommended parsing order for a single token:
- detect whether the final character is `!`
- if so, remove the trailing `!` and remember `skip_on_last: true`
- if the token is a rest token and contains `^`, split on the first `^`
- parse the left side as the rest token core
- treat the right side as the spoken rest label
- parse the remaining token core for `type`, `duration`, and optional `@countdown`
